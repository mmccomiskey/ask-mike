WHAT THIS PROJECT IS
--------------------------------------------------------------------------------

Two tracks that ship to the same site.

TRACK A - "Build an LLM from scratch"
  Write a transformer by hand in PyTorch: tokenizer, embeddings, attention,
  training loop, sampling. Train it on a corpus about me. It will be small and
  it will be bad at answering questions. That is the point. You will understand
  exactly WHY it is bad, which is the whole lesson about scale.

TRACK B - "Ask Mike, that actually works"
  The production pattern: retrieval over a curated knowledge base, plus a
  hosted model (Gemini) for the language part. This is the thing you can put
  on your resume and let people use.

Running both is deliberate. Track A teaches you what is inside the box.
Track B teaches you how the box gets used in the real world. By the end you
should be able to explain, from first principles, exactly which parts of
Track B you could have built yourself and which parts require a data center.

================================================================================
EPIC 2 - TRACK A: BUILD A TRANSFORMER FROM SCRATCH (2xx)
================================================================================
Goal: A working decoder-only transformer that you wrote line by line, trained
on your own corpus, running in a browser tab, that you can explain completely.

Ground rule for this entire epic: NO importing a model class. No
`from transformers import ...`. torch.nn.Linear and torch.nn.Embedding are
allowed. torch.nn.MultiheadAttention and torch.nn.TransformerBlock are NOT.
If you import the thing you are trying to learn, you have skipped the ticket.

Expectations, stated plainly: with a corpus of a few thousand words and a few
million parameters on a laptop, this model will produce text that sounds
vaguely like you and is largely nonsense. It will memorize rather than
generalize. That is the correct and expected outcome. AML-215 is where you
measure that failure precisely instead of being disappointed by it.

AML-207  Single head self attention, by hand
--------------------------------------------------------------------------------
Type:      Story
Est:       3h
Depends:   AML-206
Status:    TODO

The centerpiece of Track A. Take your time here. If you only deeply
understand one ticket in this project, make it this one.

Steps:
  - Linear projections for key, query, value (no bias)
  - wei = q @ k.transpose(-2,-1) * head_size**-0.5
  - softmax over the last dimension, then wei @ v
  - Print an actual attention matrix for a real sentence from your corpus and
    read it. Which characters attend to which?

Acceptance criteria:
  [ ] Written in your own words in docs/learning-log.md, no jargon copied:
      what the query is asking, what the key advertises, what the value
      carries
  [ ] You can explain why the scaling factor is 1/sqrt(head_size), in terms
      of what happens to softmax when logit variance grows
  [ ] Loss improves over AML-206

Learn:
  Attention as data-dependent weighted averaging. The weights are computed
  from the content itself, which is precisely what a fixed convolution or a
  plain MLP cannot do.

================================================================================
EPIC 3 - TRACK B: THE ONE THAT ACTUALLY WORKS (3xx)
================================================================================
Goal: A chat interface at a public URL that answers questions about you
accurately, cites its sources, declines what it does not know, and costs
approximately nothing to run.

Architecture, and the reasoning behind it:

    Browser (GitHub Pages, static)
      |
      | 1. embed the user's question
      | 2. cosine similarity against a prebuilt embeddings JSON
      | 3. select top-k chunks                    <-- all of this is client side
      |
      v
    Cloud Run proxy  (holds the API key, nothing else)
      |
      v
    Gemini API

The important insight: retrieval does not need a vector database. With a
corpus of a few hundred chunks, the embeddings are a small JSON file you
build at deploy time, and cosine similarity is about ten lines of JS. The
entire "vector DB" is a for loop. Understand this before you ever pay for
Pinecone.

The only reason a backend exists at all is that a static site cannot keep a
secret. That is the whole job of /proxy. Keep it that small.

AML-304  Client side retrieval

--------------------------------------------------------------------------------
AML-306  Cloud Run proxy
--------------------------------------------------------------------------------
Type:      Story
Est:        3h
Depends:   AML-101
Status:    TODO

Why:
  Static sites cannot hold secrets. Anything in your JS bundle is public,
  including an API key, and a leaked Gemini key gets found and abused fast.
  Cloud Run scales to zero, so an idle proxy costs nothing.

Steps:
  - Minimal service (FastAPI or Node) with two endpoints:
      POST /embed  -> proxies to the embedding model
      POST /chat   -> proxies to the chat model, streaming
  - Key from environment, injected via Secret Manager, never in the image
  - Deploy with min-instances=0
  - Confirm cold start latency and note it; it is user-visible

Acceptance criteria:
  [ ] Deployed and reachable
  [ ] `git grep` for the key across the whole repo finds nothing
  [ ] Cold and warm latency both recorded in docs/
  [ ] Local dev path documented, so you are not deploying to test

Learn:
  Why this pattern is universal in production LLM apps, and the real cost of
  scale-to-zero, which is that the first user of the day waits.

--------------------------------------------------------------------------------
AML-307  Lock down the proxy
--------------------------------------------------------------------------------
Type:      Story
Est:        2h
Depends:   AML-306
Status:    TODO

Why:
  This endpoint is a public, unauthenticated, internet-facing wrapper around
  a metered API billed to your personal card. Assume it will be found.

Steps:
  - CORS restricted to your Pages origin and localhost only
  - Per-IP rate limit
  - Max request body size and max output tokens, enforced server side
  - Reject requests whose prompt does not match your expected shape
  - Structured logging: timestamp, truncated query, token counts, latency

Acceptance criteria:
  [ ] A curl from a disallowed origin is rejected
  [ ] Hammering the endpoint gets you 429s, verified
  [ ] A hostile client cannot request 100k output tokens
  [ ] Logs let you answer "what did people ask today and what did it cost"

Learn:
  Threat modeling a public AI endpoint. The realistic attacks are quota
  exhaustion and using your key as free inference for something unrelated,
  not clever prompt injection.

================================================================================
DECISIONS ALREADY MADE
================================================================================

  Two tracks, not one
    Because "build an LLM" and "answer questions about me" are different
    problems and pretending otherwise produces a bad version of both.

  Separate repo, not inside mccomiskey-dev
    Keeps a live personal site out of the blast radius of a learning project.
    Link the two later, or move to ask.mccomiskey.dev via AML-403.

  Cloud Run proxy, not a key in the frontend
    A static site cannot keep a secret. This is also the pattern every real
    production LLM app uses, so it is worth learning properly.

  Client side retrieval, no vector database
    At a few hundred chunks a JSON file and a for loop are genuinely the
    right answer. Know the point where that stops being true (AML-304).

  Character level tokenizer for Track A
    Worse model, better teacher. Revisit in AML-203 if you disagree.
